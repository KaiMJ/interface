A goal becomes a click, and comes back as a typed result

The whole pipeline, in the order it runs, with the actual data at every boundary. One worked example throughout — the real recording in evidence/discover-e3d4f6b7 and the real replay in evidence/replay-dd1bbee1. Every value on this page is copied out of the repository, not illustrative.

The thesis: a model is present at exactly three points, and they are not the same kind of thing. Once it asserts — choosing one action per turn (stage 5). Twice it only proposes, and code then tries to refute what it said: the anchor for a step (stage 6) and the capability's contract (stage 8c). A proposal that fails the check is dropped, and the deterministic answer is used instead.

Everywhere else — including the entire production execution path — there is no model, and structurally cannot be. ReplayEngine.__init__ takes no LLM parameter at all, so it holds no reference to one, and its resolver is built allow_vlm=False, which raises if the tier is reached. Determinism is a property you can check by reading a constructor.

MODEL ASSERTS the model's word is taken MODEL PROPOSES …and code tries to refute it NO MODEL deterministic, by construction DRIFT SIGNAL emitted for free, per step NOT BUILT declared but not derived

The ask — DiscoveryLoop.run(goal, start_url, inputs)

A goal in English plus the concrete values this run will use. The inputs are not just "what to type": they are the parameter declaration. Any literal in the recording that matches one of them becomes a placeholder at stage 8b, which is how "who decided 12345 was a parameter?" gets a deterministic answer.

input
goal   = "open the profile for member 12345 and read the current
          balance of their Primary Savings account"
inputs = { "member_id": "12345",
           "account_nickname": "Primary Savings" }

The entry navigation is recorded, not merely performed — it becomes step 1 of the artifact. Without it a capability begins wherever the browser happened to be, and a second invocation in the same session starts on the previous run's member profile.

Detection knows where the controls are. OCR knows what the words are. Neither alone is enough: a bare box cannot be targeted semantically, and a bare text line is not necessarily clickable. This is the hop that makes everything above it surface-agnostic.

rule 1
Text inside a control becomes its name/text, and goes to the smallest containing control — a button inside a card is contained by both.
rule 2
Control inside the text is also a label. Measured: detector box 29×16 vs OCR line 41×23 on the same "View" button — containment only 0.49. Without this rule every button on the page is anonymous. A size guard stops an icon claiming a whole row.
rule 3
A control larger than 15% of the frame is a container and absorbs nothing. Measured: a 21%-of-frame detection on the sign-on screen swallowed both field labels and left "User ID" unaddressable.
rule 4
Text with no enclosing control survives as role="text". Not clickable — but it is exactly what anchors and checkpoints match against.

Then: NMS dedupe (highest confidence first) → re-infer role now the box has words → reassign ids e0, e1, … in reading order, top-to-bottom then left-to-right. Ids are stable within one observation and meaningless across them. Nothing may persist them.

The model decides MODEL

One call, one tool call back. The action space handed to the model is the artifact's step vocabulary — it cannot express anything replay cannot execute. That is what makes recordings replayable by construction rather than by post-hoc inference over a transcript.

in — the turn
system: role, the app's `surface` line
        from policy, allowed actions,
        the rules, the trust boundary
user:   goal, declared parameters,
        history, candidate list,
        how many were truncated
image:  the annotated overlay
out — exactly one tool call
{ "name": "click",
  "input": {
    "mark":   13,          ← a NUMBER
    "intent": "click the Search button
                after entering member
                ID 12345",
    "expect": "Member Profile",
    "anchor": "Search",   ← optional,
                          and checked
    "risk":   "safe" } }

None of the extra fields is decoration. intent is what the policy layer classifies for risk — click(0.42, 0.71) cannot be judged reversible or not — and it is what a human reviewer reads. expect is checked immediately at stage 7. anchor is the model's answer to "the shortest text on this element that will still identify it next month", and it is checked at stage 6 before it is believed.

Page text is declared untrusted input in the system prompt. That is a mitigation, not a defence: the allowlist bounds the blast radius, it does not stop the model being misled inside it.

The model supplied a number. The element behind that number supplies role, name, text and box. So Target is written from measured data, never from the model's description of what it thought it was clicking. This is the join that makes the artifact trustworthy.

  "risk": "safe",

    "intent":      "click the Search button …",

    "anchor_match": "contains",
    "role": "button",        ← tier 2
    "name": "Search",
    "bbox": { … },           ← tier 3
    "relation": "self" } }

Two cases rewrite the anchor to a neighbour, and both were found by reading a recorded artifact:

· an empty control — a form field has no text, so anchoring on it is anchoring on nothing and replay falls straight through to the recorded box.
· a value — anchoring an extraction on the value it read is self-defeating: $18,204.55 identifies this balance only until the balance changes, which for a balance is the whole point.

Which neighbour is measured, not guessed, and ranked: (1) text the caller declared as an input, (2) text appearing exactly once on screen, (3) nearest — only as a fallback, because nearest is wrong in a grid: the cell left of a balance is its status, and "Active" is on every row. Step 5 of our artifact is the result: anchor_text: "{{account_nickname}}", relation: right_of, index: 1.

…and a third case: the element's text is part durable MODEL PROPOSES

"Search" is entirely durable, so it becomes the anchor untouched. But an element's text is often part durable and part volatile, and only the durable part belongs in a recording. This is the _falsify pattern from stage 8d, applied one level down — the model may propose a shorter anchor, and code then tries to refute it.

The failure this prevents, proven before it was fixed. A dropdown option on the transfer form reads 29883 - Checking - $4,820.19. Taking the full text as the anchor, then parameterizing, produced:

anchor_text: "{{from_account}} - Checking - $4,820.19"   match: contains

That artifact dies on its own second run — a transfer changes the balance, and the anchor never matches again. The shipped read capability never exhibited it, because that flow only ever clicks buttons with short stable text ("Search", "View"). A latent bug that one recorded flow hid.

1 · a FACT
A value the caller declared as an input that appears in the element's text. Not a judgment — the caller named it as the thing that varies per invocation, which is exactly what "identifies this record" means. Free, offline, and it covers the common case. Here: 29883.
2 · a JUDGMENT
What the model proposed. Used only when the durable part is not one of the declared inputs — "the row for merchant PACIFIC WIRELESS" — where the code has nothing to go on and the model has read the screen.
both face
_identifies() — the candidate must be text actually on the chosen element, and re-resolving it against that same frame must land back on that same element with candidates == 1 and tier is ANCHOR_TEXT. A proposal that picks out a different element, or three of them, is worse than the full string — and is dropped.

Why fact beats judgment, and it is not a preference. Asked for an anchor on 29883 - Checking - $4,820.19, a model may answer $4,820.19. That text is on the element, is unique on the frame, and passes every check here — because "will this still be true next month?" is not answerable from one observation. The declared input 29883 is answerable. So it wins, and the model is never consulted.

The guardrail gate — policy.check_action(primitive, risk, intent)

The same policy object replay uses, on the same primitive, called before the action rather than after it. A guardrail that only guards the LLM is not a guardrail — and one that only guards replay is not either.

denied
Primitive not in the allowlist, URL outside the permitted patterns, or risky_disposition: block → PolicyDenied. The step is refused and recorded as refused; the model is told and tries something else.
confirm → PARK
A risky action is risky whoever is driving. The recording session parks on the same RunControl token replay uses, raises an InterventionRequest with mode="discovery", and hands the live browser to a human. Abort ends the run ESCALATED; resume writes the approval into the history and proceeds.
allow
Execute.

This was a real asymmetry until recently. The loop called check_action(...) and discarded the return value — it reacted only to PolicyDenied. So under risky_disposition: confirm, replay parked for a human and discovery executed the risky step unattended. Recording a transfer would have sailed straight through "Confirm Transfer", the one control in the app that moves money. The method returned a disposition that one of its two callers threw away.

The alternative — letting a recording session submit a transfer because a human is notionally watching a VNC window — is a guardrail that binds only the path needing it least.

The model's own escalate tool now parks the same way (AGENT_REQUESTED) instead of merely ending the run: a human can unstick it on the live session and the recording continues. On resume the model is told what happened and that "the screen may have moved; look again before acting" — without that line its next action is reasoned from a state it never saw.

A loop built with control=None (the offline tests) treats a park as a refusal, not permission. The safe reading of "nobody can be asked" is not "proceed anyway".

Was the model right? — the expect check NO MODEL

Verified immediately against the next frame, deterministically. This is why every checkpoint in a saved artifact has already passed once — on the run that wrote it.

unmet · unchanged
DISCARD the step. Nothing happened, so there is nothing worth replaying. The model is told what the screen actually reads, so its next attempt differs.
unmet · changed
KEEP the step, DROP its checkpoint, and note it for the reviewer. Dropping the step would leave the recording missing a state transition the flow actually made — replay would then start on a screen it never reaches.
met
KEEP with the checkpoint. The expected path.

The middle branch fired on the real run. Step 3 of the shipped artifact carries, verbatim:

"note": "recorded without a checkpoint: the run expected 'Member Profile'
         here and the screen showed something else. Review before approving."

The model predicted the profile would appear after clicking Search; the search-results list appeared instead. The click was real and the screen did change, so the step is kept — and the assertion it could not verify is not written into the artifact. An unverifiable claim has no business in a contract.

8

Recording becomes a contract — synthesize()

Four passes. Three are deterministic code; exactly one consults the model, and everything it proposes is then refuted by code before it survives.

a · prune
Drop steps that did not advance state — a second read of a value already read under the same name, a navigate immediately superseded by another. Conservative on purpose: anything more aggressive is deciding after the fact that a step the run verified was unnecessary. Step ids are left alone here — they are what ties an extraction to its output.
b · parameterize
Substitute declared input values with placeholders, longest match first so an input of 123 does not corrupt a recorded 12345 belonging to a different input. An input appearing nowhere in the recording is not declared — telling a calling agent it can steer something it cannot is worse than silence.
c · declare MODEL
The model writes the description, proposes a success_text, and — this one is forward-looking by design — proposes business outcomes for screens this run never visited. Describing them is the job, not a mistake.
d · _falsify
Code refutes what the model proposed. An outcome detector cannot be confirmed — the run never saw that screen — but it can be refuted: a phrase visible while the flow succeeded cannot be what distinguishes it having gone another way.
b · parameterize — real substitution
# before
value: "12345"
intent: "type the member ID 12345 …"
checkpoint.value: "12345"

# after
value: "{{member_id}}"
intent: "type the member ID
         {{member_id}} …"
checkpoint.value: "{{member_id}}"
d · _falsify — real synthesis.json
proposed 2, kept 0:

"member_not_found"
  detector_text: "Search Results"
  REJECTED — on a frame the
  successful run passed through

"account_not_found"
  detector_text: "Accounts"
  REJECTED — same reason

Both proposals were wrong, and code caught both. "Accounts" is a column header on every screen in the app — had it survived, every successful run would have been classified as account_not_found. The rejections are kept in synthesis.json rather than discarded: what was proposed and thrown away is part of judging whether the rest is trustworthy.

So cap_get_savings_balance@v1 shipped with zero business outcomes. The real one was added later by cua learn-outcome, which replays the capability twice — once with the recorded inputs, once with member_id=99999 — and takes the detector from the difference: "No member matches the search criteria entered.", the app's own wording, copied off the screen that produces it. That is @v2.

The result round-trips through its own schema before anyone is told it exists, and a model_validator rejects an artifact whose internal references do not resolve: duplicate step ids, an output reading from a step that does not extract, a {{placeholder}} naming no declared input, an undeclared screen, an uncompilable base_url_pattern. Each is otherwise an artifact that loads fine, passes review, and dies halfway through a run against a member's account.

The capability executes NO MODEL

ReplayEngine.__init__(perceiver, driver, resolver, policy, evidence, control, …) — there is no llm parameter. It cannot call a model because it holds no reference to one. The resolver it is handed is built allow_vlm=False, whose VLM method raises RuntimeError rather than degrading quietly.

in — the caller's invocation
replay(cap=cap_get_savings_balance@v2,
       inputs={ "member_id": "12345", "account_nickname": "Primary Savings" })

# validated BEFORE anything is touched: type coercion, pattern,
# min/max, choices, not_equal_to. A bad call is a rejected call, not a
# run that gets four steps in and types "None" into an amount field.

Per step, in this order:

verify permission
Policy: is this action allowed? this URL? is it risky, and does the app say allow / confirm / block? Policy can promote safe→risky from the declared intent, one-directionally — a recording that mislabels a submit as safe is the expensive failure. Identical to the discovery gate above: same policy object, same RunControl, same live session handed to the same operator.
settle + observe
Two hash-equal frames, or stable text. Same perceiver the recording used — if replay saw the screen through a different pipeline, every checkpoint written at record time would be a guess.
check screen
Is this the state the step expects? → WRONG_SCREEN, naming where it actually is. NOT BUILT Screen is declared and enforced but never derived, so recorded capabilities declare none and make no claim about where they are.
resolve
The ladder, most portable first — see below.
verify target
Does the region say what the recording said it said? Is anything stacked on top of it? Nearly free — the observation already exists.
EXECUTE
The primitive.
verify effect
Poll the checkpoint until its own declared timeout. There is no sleep() on this path with exactly one exception: a recovery the policy explicitly declares as a wait. "Not true yet" and "not true" are the same picture, so they get the same loop.
resolve — the ladder, and what fired on the real run

                   which is what makes data-dependent targeting possible.
                   Survives rebranding and relayout.        ← all 4 targeted

# no tier matched → Unresolvable, terminal. It does NOT fall back to the
# recorded box as a last-ditch guess: a step that cannot find its target has

DRIFT SIGNAL   The tier that succeeded is recorded on every step result. Aggregated across runs, anchors decaying into recorded_bbox means the application moved — an early warning that costs nothing and arrives long before a hard failure.

classify() — one function, called after every step. The order is load-bearing.

1 · outcomes
[ARTIFACT]   First, always. If the checkpoint ran first, "no such member" would be reported as a failed assertion instead of the answer the caller asked for. → BUSINESS_OUTCOME, clean stop.
2 · recoveries
[POLICY]   Apply the handler, re-observe, retry. Bounded by max_per_run: dismissing the same modal eleven times means the dismissal is not working, and that is a hard failure, not eleven successful recoveries.
3 · declared
[POLICY]   app_errors and escalations, split by who can clear it. Before the checkpoint on purpose — both would otherwise arrive as "the checkpoint did not hold", which describes the symptom and hides the cause.
4 · checkpoint
[ARTIFACT]   The expected path. → OK.
5 · anything else
HARD FAILURE. Not a gap: under vision-first perception we cannot enumerate every screen an enterprise app can produce, and guessing at an unknown state in a banking application is worse than stopping.

Where each detector lives is the multi-tenant argument in miniature. Business outcomes belong to the capability — they are answers one flow can return. Recoveries, app errors, escalations and the sign-on recipe belong to the app policy — a session interstitial interrupts every flow on the app, and copying it into each artifact would guarantee they drift apart. Session expiry is deliberately an escalation, not a recovery: re-authenticating mid-flow means the automation holds credentials and silently resumes a run whose context may no longer be valid.
